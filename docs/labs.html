Bring your domain problem. The stack below is yours to use for your ordinary work, extend, publish from and build instruments on. Contribute back what turns out to be useful. You do not have to become a theorist of anything.

the common stack

Layer 7
Applications
domain tools, notebooks, models, UI, dashboards
Layer 6
Humanesque components
PANINI, ILM, PEDLER, PRATIK, VIDYA, PAT.AL, AyeAM — as needed, never all

GENIE orchestration
composition, tool use, persistent state, cross-domain execution
Layer 4
Research software stack
Python, Julia, R, C/C++, MATLAB-compatible workflows, domain libraries, simulation engines
Layer 3
Container runtime
Docker or Podman, compose, Kubernetes where the work needs it
Layer 2
OS, drivers, firmware
Linux, CUDA/ROCm, hardware interfaces, device permissions
Layer 1
Hardware
laptop → workstation → rack → cluster; GPU, CPU, FPGA, MCU, sensors
Layer 0
Physical world
instruments, experiments, environments, real-world systems

Each domain receives a reproducible, dockerised research environment. NOT every domain gets every component. Keep it minimal and fit for purpose.

Every cost above is 'not established' until a bill of materials is priced with core.bom, where a quote carries its source and its timestamp and an unpriced line blocks the total. 'Low cost' is a measurement, not an adjective.

the Holy Grail loop

Research → Formalisation → Simulation → Prototype → Experiment → Instrumentation → Observation → Evidence → Verification → Revision → Improved architecture

The loop returns to architecture. The lab improves the lab factory — that is the recursive part.

Every claim a lab makes enters at a rung from core.rungs (SPEC, MODEL, SIMULATED, BENCH, FLIGHT) and cannot be read above the rung it entered at. Promotion requires an artifact in the tree.
